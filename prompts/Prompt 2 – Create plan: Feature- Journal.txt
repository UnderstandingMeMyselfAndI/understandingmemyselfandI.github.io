You are a senior software architect and product engineer specializing in privacy-first Progressive Web Apps (PWAs), React + Vite codebases, offline-first architecture, and recovery/mental-health applications. Your task is to produce a clear, actionable, phased development plan for adding **one** new feature to an existing production PWA: **Journal**.

============================================================
1. APPLICATION CONTEXT (do not deviate from these constraints)
============================================================

App name / URL: UMMI (https://app.ummi.now)
Purpose: Companion PWA for people in addiction recovery. Extremely privacy-focused – no remote data storage by default. All user data stays on-device.

Tech stack & conventions (MUST be followed):
- Frontend: React (JSX) + Vite
- Styling: Sass (.scss). Every component has a matching .scss file with the same name, lowercase first letter (e.g. Journal.jsx → journal.scss)
- State management: Zustand
- Local storage: IndexedDB only (no remote writes unless explicitly consented)
- Hosting: Cloudflare Workers with GitHub Actions CI/CD
- Repository: GitHub
- Existing navigation: controlled by Zustand store + NavBar.jsx
- New features are implemented as full-screen “Activities”
  - Location: src/components/activity/<activity-name>/
  - Must start from the template files in src/components/activity/template/Template.jsx
  - Rename the template to match the practical function of the activity
  - All UI code goes between the <section> tags of the template
  - Register the new activity in the main navigation via the Zustand store / NavBar

Non-negotiable quality requirements:
- Code must be extensible, reusable where possible, and performant on entry-level mobile handsets through to flagship devices
- UX/UI must be simple and intuitive. Remove superfluous steps. Prefer sensible defaults over asking the user. Prefer yes/no decisions when a choice is unavoidable.
- Re-use existing UI elements/assets wherever possible; invent new ones only when strictly necessary
- All user-facing strings live in flat .js files under src/data/ named <FeatureName>Data.js (or <FeatureName>DataN.js if collision). Objects + arrays only.
- Data may later move to a headless CMS or remote servers. Design storage layer so that remote backends can be added later without rewriting feature logic. If remote is ever used, the user MUST explicitly confirm; record timestamp, device details, IP, and a descriptive title of the consent.
- Always save user data to local storage as it changes. Use the least storage possible; compression is allowed only if it has no noticeable impact on read/write.
- The app must track total storage used and remaining space. Warn the user when space is low and offer concrete management recommendations.
- Connectivity awareness: if a feature needs the network, monitor connection quality. Surface a simple UI message (max update frequency = 5 s) when connectivity is lost, restored, slow, or problematic.
- Security (applies to every feature that stores personal data):
  - All data encrypted at rest and in flight (when remote is used)
  - GDPR-compliant
  - Latest encryption standards for personal data
  - 6-digit passcode OR strong password required to access/view personal data
  - Passcode/password creation, login, and change flows must be simple and intuitive
  - User must be warned that forgotten credentials = permanently lost data (because everything is local)
  - If the user has not set a passcode/password and tries to enter personal data → prompt them to create one
  - Reminder to set a passcode/password appears at most once per day
  - Discreet UI indicator when data is currently unsecured
  - User can enable security at any time
  - Implement a “dry-run” / test mode for the passcode + encryption system so the developer can verify lock-out behaviour without losing real data
- Every new feature that stores personal data MUST implement the passcode/password gate.

============================================================
2. FEATURE TO PLAN – Journal
============================================================

Requirements:
- User can add, view and edit journal entries.
- Three clear user steps / screens:

  1. Journal overview
     - List of journal entry titles
     - Colour-coded feelings badges
     - Edit button
     - Modified date + creation date
     - Tapping an entry or the edit button opens the Edit screen
     - A clear “Create new entry” action (icon or button) is always visible

  2. Create new journal entry
     - Triggered by the create action on the overview screen
     - Opens a blank Edit screen pre-configured for a new entry
     - User can immediately start typing title and content
     - Feelings tags can be added
     - On save, the new entry is written to IndexedDB and the user is returned to the overview (or stays on the edit screen – choose the simplest, least friction path)

  3. Edit existing journal entry
     - Title field
     - Content field
     - Ability to add / remove tags that represent the user’s feelings
     - Save updates the existing entry (modified date is refreshed)

- The create flow must feel instantaneous and low-friction (no extra confirmation screens unless required for security).

Produce a complete development plan that a senior React engineer can execute. Structure the plan as follows:

1. High-level architecture decisions
