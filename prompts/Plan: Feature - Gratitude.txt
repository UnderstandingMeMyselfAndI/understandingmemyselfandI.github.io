Development Plan: The Little Book of Small Wins (UMMI PWA)
1. High-level architecture decisions
Integration with existing systems

Activity lives at src/components/activity/smallWins/SmallWins.jsx (renamed from template/Template.jsx).
All UI content is placed strictly between the existing <section> tags of the template.
Register the activity in the existing Zustand navigation store (the same place other activities are registered) and surface it in NavBar.jsx. Use a stable activity key such as "smallWins".
Reuse the shared security gate (passcode/password + encryption) that every personal-data feature must implement. The activity never renders personal content until the gate is satisfied.
All persistence goes through a thin local storage abstraction layer that currently writes only to IndexedDB. The abstraction is designed so a remote backend can later be plugged in without touching feature logic; any remote write requires explicit user consent (timestamp, device details, IP, descriptive title) which is recorded locally first.
Always write on every change (create / edit / delete). Prefer the smallest possible JSON payload; compression is allowed only if it has zero noticeable latency on read/write for entry-level devices.
Storage-quota monitoring is a shared utility (see Phase 0). The activity subscribes to it and surfaces the existing low-space warning + concrete management recommendations when remaining space is low.
Connectivity: this feature is fully offline-first. No network calls are required. If a future remote-sync option is added, the shared connectivity monitor (update frequency ≤ 5 s) will surface the standard “connection lost / restored / slow” UI messages.

IndexedDB schema (versioned)

Object store: smallWins
Key path: id (UUID string)
Indexes: date (ISO date string, for chronological listing), createdAt, updatedAt

Object store: smallWinsPeople (names stored separately for reuse)
Key path: id (UUID string)
Index: nameLower (for case-insensitive type-ahead)

Object store: smallWinsMeta (optional single-record store for feature-level flags if needed later)
Versioning: bump the shared IndexedDB version number when these stores are added. Migration simply creates the new stores; existing data is left untouched. The storage abstraction exposes getDB(), put(), getAll(), delete(), queryByIndex() so the feature never talks to IndexedDB directly.

Encryption & passcode integration points

Before any read or write of smallWins / smallWinsPeople data, the shared security gate is checked.
Encryption key is derived client-side from the user’s passcode/password (see section 3). Ciphertext is what is written to IndexedDB.
Dry-run mode (developer-only) uses a separate key and a throw-away IndexedDB database so lock-out behaviour can be verified without touching real data.

Storage-quota monitoring strategy

Shared utility (src/utils/storageQuota.js) that periodically (or on every write) calls navigator.storage.estimate() and exposes { used, remaining, percent } via a Zustand slice or a React context.
When remaining space falls below a configurable threshold the activity (and any other personal-data feature) shows the existing low-space banner with concrete recommendations (delete old wins, clear other activities, etc.).

Connectivity monitoring strategy

Not required for the core feature. If a future “share” or “remote backup” path is added, reuse the existing shared connectivity monitor (max 5 s update frequency) and surface the standard UI messages.

User flows

Happy path: open activity → gate passes → list of previous wins → “Add” → fill form (title, description, date default today, who-with type-ahead) → save → list updates, data written encrypted.
No passcode set: first attempt to enter personal data → prompt to create passcode/password (shared flow). Reminder appears at most once per day.
Low storage: after any write that crosses threshold → banner with concrete recommendations.
Offline: fully functional; no network dependency.
Forgotten passcode: shared warning on login screen (“forgotten credentials = permanently lost data”).
Type-ahead: as user types in “Who with”, matching names from smallWinsPeople appear; selecting one reuses the existing person record; typing a new name creates a new person record on save.
Edit / delete: same form for edit; delete requires a simple confirmation (yes/no).
Empty state: friendly copy + single prominent “Add your first small win” button.

Reusable components to extract

PeopleTypeAhead – pure controlled component that accepts value, onChange, suggestions, onSelect. Suggestions come from a small Zustand slice or direct IndexedDB query filtered by the typed prefix. This component is designed for reuse by any future activity that needs people names.

Strings (all live in SmallWinsData.js)

Activity title, form labels (“Title”, “What happened?”, “Date”, “Who with”), buttons (“Save”, “Cancel”, “Delete”), empty states, educational sections (“Why Small Wins Matter”, “Examples”, “How to Practice”), low-storage messages, security prompts (reuse shared strings where possible), type-ahead placeholder, confirmation dialogs.

3. Security & privacy implementation plan

Passcode / password flows (shared, already required by every personal-data feature)
Creation: simple 6-digit passcode or strong password; confirmation step; immediate encryption of any existing unsecured data.
Login: on every app start / activity open that needs personal data.
Change: current credential → new credential → re-encrypt.
Dry-run / test mode: separate key material + throw-away IndexedDB database; accessible only in development builds.

Reminder: “Please set a passcode” appears at most once per calendar day (persisted flag in local meta store). Never blocks the user; just a gentle banner.
Unsecured-data indicator: discreet icon / subtle text in the activity header (and globally if desired) when personal data exists but no credential is set.
Encryption approach (pure client-side)
Derive a master key from the user’s passcode/password using a memory-hard KDF (Argon2id or PBKDF2 with high iteration count – choose the strongest that still performs acceptably on entry-level Android WebViews).
Store only the salt + encrypted data keys in IndexedDB. The derived key never leaves memory for longer than needed.
Encrypt each record with AES-GCM before writing; decrypt on read after the gate has passed.
Compatible with the existing IndexedDB abstraction; the feature code never sees plaintext outside of the React component tree while the gate is open.

Technical risks & mitigations

IndexedDB size limits / quota on older Android WebViews → storage-quota watcher + concrete management recommendations; keep payloads tiny.
Encryption performance on entry-level phones → choose a KDF that still finishes in < 300 ms on low-end hardware; measure; fall back to a slightly weaker but still acceptable parameter set if necessary; keep key derivation off the critical path after first unlock.
Type-ahead query latency when the people store grows large → index on nameLower + limit results to top N matches; virtualise if ever needed.
Accidental data loss from forgotten credentials → very clear, repeated warning on the login and creation screens (already required by the security constraints).
