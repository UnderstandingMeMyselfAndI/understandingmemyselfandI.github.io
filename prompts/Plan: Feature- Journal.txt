Journal Feature – Development Plan for UMMI PWA
1. High-level Architecture Decisions
Integration with existing systems

New activity lives at src/components/activity/journal/.
Start from src/components/activity/template/Template.jsx. Rename/copy to Journal.jsx (and matching journal.scss). All UI lives inside the template’s <section> tags.
Register the activity in the existing Zustand navigation store and NavBar.jsx exactly as other activities are registered (add entry to the activities list / route map).
Use the shared security gate (passcode/password) that every personal-data feature must implement. Journal never renders its list or editor until the gate is satisfied.
All reads/writes go through a thin storage abstraction layer (IndexedDB only by default). The abstraction must accept a future remote backend without changing feature logic. Any remote write requires explicit user consent (timestamp + device details + IP + descriptive title) recorded locally.
Storage-quota monitoring is shared; Journal participates by reporting its own usage and reacting to global “low space” events.
Connectivity monitoring is not required for core Journal (purely local). If a future export/sync is added, it must use the shared connectivity watcher (max UI update every 5 s).

IndexedDB schema

Database name: reuse the existing app database (or create ummi-db if none exists). Version bump strategy: increment on schema change; use onupgradeneeded to create/migrate stores.
Object store: journalEntries
Key path: id (UUID string generated client-side).
Indexes:
by-created (createdAt, unique: false)
by-modified (modifiedAt, unique: false)
by-title (title, unique: false) – optional for future search

Value shape (encrypted at rest):JavaScript{
  id: string,
  title: string,
  content: string,
  feelings: string[],          // array of feeling keys
  createdAt: number,          // Unix ms
  modifiedAt: number,         // Unix ms
  // future-proof fields
  version: 1
}

Encryption: entire value (or sensitive fields) encrypted with a key derived from the user’s passcode/password before put. Decryption on read. Store never holds plaintext personal data.
Quota tracking: after every write/delete, call shared updateStorageUsage() that sums sizes of all stores and exposes remaining quota via the Storage Manager API (navigator.storage.estimate()).

Encryption & passcode integration points

Key derivation: PBKDF2 / Argon2id (prefer Web Crypto) with high iteration count + random salt stored in a separate non-encrypted store or in the same DB under a protected key.
Passcode gate wraps the entire Journal activity. On first personal-data access without credentials → force create flow. Subsequent opens → unlock flow.
Dry-run mode: developer flag (or query param) that uses a temporary in-memory key and never touches real data.

Storage-quota monitoring

Shared utility already (or to be) present: src/utils/storageQuota.js.
Journal calls it after every mutation. When remaining space < threshold (e.g. 10 % or absolute MB), surface a non-blocking banner with concrete actions (delete old entries, export then delete, clear other activities).

Connectivity

Not required for MVP. If later added, use shared useConnectivity hook that surfaces a simple toast (max once per 5 s).

3. Security & Privacy Implementation Plan

Passcode/password creation, login, change: reuse (or implement once in Phase 0) shared components:
Create: simple 6-digit or strong-password form + confirmation + “forgotten = data lost forever” warning.
Login: same fields + unlock.
Change: current + new + confirm.

Reminder to set passcode: appears at most once per calendar day (store last-shown timestamp in local storage). Triggered on Journal open if no credentials exist.
Unsecured indicator: small lock-open icon in the activity header (and optionally global nav) when data is unsecured.
Encryption:
Derive key from passcode via Web Crypto (PBKDF2 with high iterations + salt).
Encrypt entry objects with AES-GCM before IndexedDB write.
Key never persisted in plaintext; kept in memory only while unlocked (or derived on demand).
Dry-run mode: ?dryRun=true or feature flag that uses a fixed test key and a separate in-memory / temp store so real data is never touched.

2. Auto-save (no explicit “Save” button)
Yes – the original plan is updated.

Journal now uses continuous auto-save:

On every meaningful change (title, content, feelings) a debounced write (300–500 ms) occurs.
Create flow: tapping “Create new entry” immediately inserts a new unique row in IndexedDB with empty title/content and current timestamps. The Editor opens against that live row.
Edit flow: opens the existing unique row.
There is no separate “Save” action or confirmation screen. The only explicit actions are “Done / Back” (returns to Overview) and optional “Delete”.
Visual feedback: subtle “Saved” indicator that appears briefly after each successful write (or a persistent “Saving…” while the debounce is pending).
This keeps the create path instantaneous and low-friction as required.

3. Cancel / discard behaviour + unique rows

Every journal entry is a distinct, permanent row in the journalEntries object store (unique id).
Create always produces a new row immediately.
“Cancel” is only relevant while editing an existing entry:
If the user has made changes, a soft confirmation appears (“Discard changes?”) that reverts the in-memory draft to the last-persisted version (or reloads from IndexedDB).
Empty new entries that the user never typed into can be auto-deleted on leave if desired (optional, low-friction default: leave them; user can delete later).

No soft-draft concept outside of the live unique row.

4. Date display

Relative (“2 h ago”, “Yesterday”, “3 days ago”) when the timestamp is < 24 h old.
Absolute (e.g. “6 Oct 2026, 14:32”) once ≥ 24 h old.
Both created and modified dates follow this rule. Implementation: small pure utility formatJournalDate(ts).

5. Maximum entry length
500 words is a reasonable soft limit for a recovery journal:

Keeps individual entries focused and storage-light.
Still allows meaningful reflection.
Recommendation in the plan: soft warning at ~450 words (“Approaching length limit – consider starting a new entry”) and a hard block (or very strong warning) at 500 words.
Exact word-count utility: simple split on whitespace; ignore pure whitespace.
Storage impact of 500 words is negligible even on low-end devices, so the limit is primarily UX, not technical.

3. Security & Privacy Implementation Plan

Passcode/password creation, login, change: shared components (create, unlock, change, dry-run).
Daily reminder to set a passcode: appears at most once per calendar day (last-shown timestamp stored locally). Triggered on Journal open if no credentials exist.
Unsecured indicator: small lock-open icon in the activity header while no passcode is set.
Encryption:
Derive key from passcode via Web Crypto (PBKDF2 + salt).
AES-GCM encrypt entire entry before IndexedDB write.
Key kept in memory only while unlocked.

Dry-run mode: ?dryRun=true or feature flag uses a fixed test key + temporary store so real data is never touched.
User is warned on every auth screen that forgotten credentials = permanently lost data.

6. Open Questions / Risks
Open questions (remaining)

Should completely empty new entries (never typed into) be auto-pruned on leave, or left for the user to delete later? (Current default: leave them.)
Exact wording of the length warnings and discard confirmation (can be finalised in JournalData.js).

Technical risks & mitigations

IndexedDB size limits on older Android WebViews → aggressive quota monitoring; offer export/delete; 500-word soft limit keeps individual entries small.
Encryption performance on entry-level phones → Web Crypto AES-GCM + measured PBKDF2; dry-run mode for safe testing.
Key loss = permanent data loss → repeated clear warnings + dry-run mode.
Auto-save debounce too aggressive or too slow on low-end devices → measure and tune (default 300–500 ms); visual “Saving…” indicator prevents user confusion.
Future remote backend → storage abstraction already isolates feature logic; consent recording is mandatory.
