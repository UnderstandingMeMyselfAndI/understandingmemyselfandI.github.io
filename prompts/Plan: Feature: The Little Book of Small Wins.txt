Complete Development Plan: The Little Book of Small Wins (UMMI PWA)
1. High-level architecture decisions
Integration with existing systems

Activity lives at src/components/activity/smallWins/SmallWins.jsx (copied and renamed from src/components/activity/template/Template.jsx).
All UI code is placed strictly between the existing <section> tags of the template.
Register the activity in the existing Zustand navigation store with the stable key "smallWins" and surface it in NavBar.jsx.
Reuse the shared security gate (passcode/password + encryption). The activity never renders personal content until the gate is satisfied.
All persistence goes through the shared local storage abstraction layer (IndexedDB only by default). The abstraction is designed so a remote backend can later be added without rewriting feature logic. Any remote write requires explicit user consent (timestamp, device details, IP, descriptive title) recorded locally first.
Always write on every change (create / edit / delete). Prefer the smallest possible JSON payload.
Storage-quota monitoring is handled by the shared utility. The activity subscribes and surfaces the existing low-space warning + concrete management recommendations when space is low.
Connectivity: fully offline-first. No network calls required for core functionality. The export path is also pure client-side.
Primary CTA: prominent “Add a small win” button that opens the create form.

IndexedDB schema (versioned)

Object store: smallWins
Key path: id (UUID string)
Indexes: date (ISO date string), createdAt, updatedAt

Object store: smallWinsPeople (names stored separately for reuse and type-ahead)
Key path: id (UUID string)
Index: nameLower (case-insensitive type-ahead)

Versioning: bump the shared IndexedDB version when these stores are added. Migration creates the new stores; existing data is left untouched. Feature code never talks to IndexedDB directly — it uses the shared abstraction (getDB(), put(), getAll(), delete(), queryByIndex()).

Encryption & passcode integration points

Before any read or write of smallWins / smallWinsPeople data, the shared security gate is checked.
Encryption key is derived client-side from the user’s passcode/password.
Ciphertext is what is written to IndexedDB.
Dry-run mode (developer-only) uses a separate key and a throw-away IndexedDB database so lock-out behaviour can be verified without touching real data.

Storage-quota monitoring strategy

Shared utility (src/utils/storageQuota.js) that calls navigator.storage.estimate() and exposes { used, remaining, percent }.
When remaining space falls below the configured threshold the activity shows the existing low-space banner with concrete recommendations.

Connectivity monitoring strategy

Not required for the core feature or the export path (both are fully client-side).

User flows

Happy path: open activity → gate passes → see list (newest first) → tap “Add a small win” → fill form (title, description, date default today, multiple people via type-ahead) → save → list updates, data written encrypted immediately.
No passcode set: first attempt to enter personal data → prompt to create passcode/password. Daily reminder appears at most once per day (filler text).
Multiple people: type-ahead suggests existing names; selecting adds a chip/tag; new names create a person record on save.
Search / filter: typing in the search bar immediately filters the list client-side across title + description.
Educational content: user switches between the three tabs/buttons; content is static and pulled from SmallWinsData.js.
Edit / delete: same form for edit; delete requires simple yes/no confirmation.
Empty state: friendly copy + prominent “Add your first small win” button.
Low storage: banner with concrete recommendations after any write that crosses the threshold.
Offline: fully functional.
Forgotten passcode: shared warning that data is permanently lost.
Export: pure client-side text generation is implemented and tested but the UI control is hidden (can be revealed later with a one-line change).

Reusable components

PeopleTypeAhead – controlled component with suggestions, multi-select support (chips/tags), and creation of new names. Designed for reuse by any future activity.
EducationalTabs – simple tab/button group that shows one static section at a time.
WinSearchFilter – controlled search input + optional filters.

Strings

All user-facing text lives in src/data/SmallWinsData.js (see model above). Security-related filler strings are temporary and easy to replace.
3. Security & privacy implementation plan

Passcode / password flows (shared)
Creation, login, change, and dry-run modes follow the existing shared implementation.
User is always warned that forgotten credentials = permanently lost data.

Reminder: “Set a passcode…” (filler) appears at most once per calendar day. Non-blocking.
Unsecured-data indicator: discreet, non-blocking placement in the header secondary area (or subtle top banner). Filler text: “Data not locked”. Easy to restyle later.
Encryption
Key derived client-side with a memory-hard KDF (strongest that still performs acceptably on entry-level devices).
AES-GCM for each record.
Feature code never sees plaintext outside the React tree while the gate is open.
Dry-run mode uses separate key material + throw-away database.
